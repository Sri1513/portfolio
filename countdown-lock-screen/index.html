How a milestone gets checked off

A milestone is not checked off because its date passed. It is checked off because the database says the step happened. The database-driven check-off is in build now, completing by midnight tonight.

  • Job saved — done when the job exists in PostgreSQL. It is in the database, so it is done.
  • Fit Check Passed — done when Gemini’s fit score is on the row. No score, no check.
  • Tailored package built — done when the tailored resume, cover letter, and outreach exist for the job.
  • Application submitted — done when the application status reads submitted and the submitted time is stamped.
  • Follow up if no receipt / Reply expected — these are not check-offs. They are dates the system watches: the follow-up goes out if no receipt arrives, and the reply window is anchored to the deadline.

Today the page still checks a milestone off when its date passes. These rules replace that tonight.

How it works — eight stages, end to end

Scheduled scrapers (JobSpy for LinkedIn, Dice) plus Gmail job-alert pipelines pull new Data Engineer postings into the system, deduplicated on arrival. The real posted date is captured from the source — never the day the system happened to save it.

Latest batch, Nov 23: 21 jobs scraped, 3 new ones saved.

↓

PostgreSQL 16 holds ~2,454 saved jobs. Each row carries the title, company, location, full description, posted date, fit score, and application status. Nothing the phone shows is typed by hand — it is read from this database.

↓

A zero-cost local TF-IDF pre-score filters the noise first, then the Gemini API deep-evaluates fit and updates the row. The chain fails over: Gemini flash-lite → Groq → paid Gemini 2.5-flash.

The Amazon role scored 29/100. That number is hidden from the contest display only — it is never rewritten anywhere.

↓

For roles worth pursuing, a RAG layer (pgvector, 6,179 job chunks, hybrid search + semantic dedup) and a LangGraph tailoring agent build the tailored resume, cover letter, and recruiter outreach — from the full live job description, never from a summary. Every draft passes a human review gate before anything is sent.

↓

Every job gets a 7-day deadline counted from its real posted date, derived server-side at 23:59 America/New_York. Amazon was posted Nov 21, so its system deadline is Nov 28. The Dec 7 date in the contest link is the showcase deadline for the entry — 14 days from the entry, matching the title.

↓

GET /lockscreen renders any saved job as its own countdown screen. GET /api/lockscreen/current serves the one job that matters most right now: the highest-fit live job whose deadline hasn’t passed — or the job pinned by hand. The milestones are computed backward from the deadline: saved, fit check, package built, submitted, follow-up, reply expected.

↓

A worker runs daily (09:00 VM time). It moves expired jobs into a separate deadline queue, re-checks each posting page for real — an unreachable page reads as “unknown”, never “closed” — and marks it closed, rejected, or applied. When the current job leaves for a verified reason, Gemini drafts a WhatsApp notification saying what left, why, and what’s next. Expiry alone stays silent.

↓

The wallpaper app polls the current-job endpoint every time the lock screen shows and reloads only when the job changes. If the endpoint is unreachable it falls back to the saved link — never a blank screen. Backgrounds (glow, mist, fog, forest, rain, custom image) are picked in the app’s settings. A website cannot set a phone’s wallpaper by itself — the app is the honest route.

Gemini is the operator

MCP client

Gemini calls the 14 MCP tools on mcp.sriomkar.com — searching jobs, staging them, pinning the lock-screen job. Verified Nov 23: Gemini cleared the old pin and pinned the Commonwealth job, and the endpoint served it within the minute.

Gemini API drafting

Fit evaluation, tailoring drafts, and advance notifications all run on the Gemini API, with Groq as failover. The models reason; the database remembers; a human approves.

Human stays in charge

The machine never submits, sends, or applies on its own. Final look, submit tap, and pin are the owner’s — the system does the heavy lifting, he makes the calls.

Runs on one Oracle Cloud VM — dashboard, MCP server, and PostgreSQL behind Cloudflare. The AI runs on the Gemini and Groq clouds.
